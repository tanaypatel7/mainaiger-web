## 1. Terminal panel (`4f9313a`)

**What:** a command box in the inspector. One line runs *inside* the chosen
session's container (the same sandbox as cells: no network, read-only
workspace, the session's CPU/memory limits), output and exit code appear in the
panel, and each line is recorded in the Log.

**How:** `sessions.py` `command()` wraps the line as a Python cell that calls
`subprocess.run(["sh", "-c", line])` through the kernel, so there is no second
process type and no new privilege; `POST /api/sessions/command`. On a paired
device the same route runs there.

**Why:** you asked for a Jupyter-like terminal. Running it through the session
keeps the rule "nothing runs on this Mac that you did not approve": the
container is the only place a command can run.

## 2. Form cells (`ae67dc9`)

**What:** a cell can carry fields (text, number, integer, flag, choice) drawn
on its card; when the cell runs, each field becomes a variable before the
cell's own code. "▶▶ Run with these values" on the card.

**How:** `graph.py` `form_config/form_bindings/form_prelude`; `graph_run.py`
prepends the bindings to the source; the FORM section of the inspector edits
the fields as `name: type = default` lines.

**Why:** this is the smallest "GUI element tied to code": the field *is* the
variable. Everything later that puts a control on a card (the map's generated
cells, model-cell settings) uses it.

## 3. Devices (`84843a4`)

**What:** pair another machine that runs this same Lab (your Nexus): name, SSH
host alias, the port its Lab listens on, and a private file with its owner
key. *Connect* starts `ssh -N -L 127.0.0.1:PORT:127.0.0.1:PORT host` (shown
first), signs in, and the device's sessions appear in the Resources table
with a device column; a cell can "run on" `nexus/main`; the terminal and the
Files panel can point at the device; the device's journal is readable.

**How:** `devices.py` (`DeviceManager`, `Tunnel`, 0600 rules for the key file,
`devices.json` 0600), `remote.py` (`RemoteLab` HTTP client, `RemoteKernel`
adapter that looks like a local kernel to the run engine), `sessions.py`
`attach/sync_remote/start_remote`. The remote Lab stays loopback-only on its
own machine; nothing opens a public port. Same port on both ends because the
Lab checks the Host header.

**Why:** the vision is "choose which code uses which device". The run engine
did not change: a device session is one more kernel.

**Unverified:** the real Mac ↔ Nexus pairing. The Devices page has the install
steps; tests pair two in-process Labs.

## 4. Code map (`5d1cdbd`)

**What:** `/map` draws the Lab's own package (or any folder from Files) as a
graph: a column per module, its classes, functions and methods inside; arrows
for calls, imports, HTTP routes → handlers, and UI files → routes. Click
anything to read its source; search, collapse, toggle edge kinds.

**How:** `codemap.py` reads every `.py` with `ast` (functions, classes,
imports, calls resolved to definitions inside the folder), finds the Lab's
routes by reading `do_GET/do_POST` for the paths they compare against, and the
UI's `api('/api/…')` calls by pattern. Static only: dynamic calls are counted,
not drawn. `GET /api/codemap`, `/api/codemap/source`.

**Why:** "see MainAIger as a graph" and the base for "eat any repo". Later in
the day it found a real regression by itself (a test on the map noticed that
a call had moved during the engine rewrite).

## 5. The self-improvement example (`0964292`, then `a8c1b46`)

**What:** `examples/self-improve.ipymb`: Load → Features → Split → Train
(baseline) → Evaluate → **Propose** (a model rewrites the training cell) →
**Apply to copy** (the proposal runs on a copy of the session's variables,
never the baseline) → **Judge** (a model reads the numbers: keep / revert /
ask) → Report. After `a8c1b46` it has a **loop arrow** Judge → Propose that
fires while the verdict is not "keep", at most twice, and each new proposal
prompt carries the previous attempt's numbers.

**Found while building it:** `{{output:Apply to copy}}` was left literal
because the placeholder pattern did not allow spaces in a cell title; fixed.

**Why this shape:** it improves a *function*, not the Lab's repository, so no
step can touch your files; it proves the plumbing (a model reads a result,
answers in a fixed shape, the answer drives code and the loop, every step is
on the canvas and in the Log). The repository version is `AI_HARNESS.md` §3.

**Status:** runs in CI with a fake model (a bad proposal, then a good one);
*unverified with a real Ollama model* until you run it.

## 6. Loop arrows and conditions — the trigger engine (`a8c1b46`)

**What:** an arrow can carry a condition (one Python expression); an arrow
drawn backwards is a loop arrow with a budget. Cells behind an arrow that did
not fire are `idle`. The review dialog lists every loop and condition the run
will decide; the Log records each decision.

**How:** a new kernel op `evaluate` answers an expression in the cell's
session without running a cell (`kernel.py` protocol 2, `kernel_session.py`,
`POST /api/sessions/evaluate` for devices). `graph.py` validates `when`,
`loop`, `max_fires` and orders the forward arrows only. `graph_run.py` is a
small engine: visit cells in trigger order; a cell runs when an arrow into it
fired; a loop rewinds its body to pending; `MAX_STEPS` (500) is the hard cap.
On the canvas: dashed purple loop arrows around the right side with `↻ n/max`,
`when …` labels, a wide invisible hit area so arrows are easy to click, a
SELECTED ARROW panel.

**Why:** this was item 4 of your original list and the thing the
self-improvement loop needed to repeat itself. The rule "the arrows always
mean the same thing" was kept: Run selected honours the arrows between the
selected cells.

## 7. Start events (`14dce35`)

**What:** the Start node lists what may fire the Mainbook: a timer, a file
under the workspace changing, a chat prompt on the Models page, the Fire now
button. **Arm…** shows a review dialog that lists each source in a plain
sentence and the budget; arming ends on disarm, on an edit to cells, arrows or
sources, or when the Lab stops (never saved).

**How:** `events.py` (`EventRegistry`: a 0.5 s daemon tick, timers, file
polling every 2 s with standard-library `os.stat`, a queue of at most 10,
timer ticks coalesced); a firing calls the same `start_graph_run('all')` as
the Run button with `bindings` (`event`, `now`/`path`/`prompt`) executed in
the active session first. `GET /api/events`, `POST /api/events/arm|disarm|fire`;
the chat route fires when a chat source is armed. The Graph page notices runs
it did not start and shows them.

**Why:** "experiments that run themselves" without giving up "nothing runs
that you did not approve": arming *is* the approval, listed in full.

## 8. Map → cell (`00a0ba0`)

**What:** select a function on the Map, press **Make a cell from this…**, and
the open Mainbook gets a form cell: one field per parameter (typed from
defaults/annotations) in front of generated code that imports the function
and prints the result.

**How:** `codemap.py` now records `params` and `module` on function nodes;
`cell_for()` writes the cell; `POST /api/codemap/cell` queues it; the Graph
page's `takeInbox()` adds it through the same path as "+" and takes it from
the inbox. The generated code adds `/workspace/…` (inside the session) or the
host folder to `sys.path`, whichever exists.

**Why:** your question "how to tie GUI elements to repo endpoints so new repo
code is integrated" — this is the first mechanical answer, without a model.
