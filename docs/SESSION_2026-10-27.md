## 0. Orientation: what the Lab is today, end to end

So that the three items below make sense, here is the whole pipeline as it exists
now, with the file that owns each step.

1. **You open the Mac app.** `launcher` → owner key → `local_lab/server.py` starts
   on a loopback port and serves `local_lab/ui/*`. Every request needs the owner
   session cookie and a CSRF token; nothing is reachable from the network.
2. **You open a Mainbook** (`/graph`). A Mainbook is one `.ipymb` file
   (`local_lab/graph.py`: a standard Jupyter notebook + `graph` + `layout`). The
   canvas (`local_lab/ui/graph.js`) shows the same cells as cards; **control
   edges** are triggers ("B runs when A finished ok"); **data edges** are derived
   by reading the code (`graph.analyze`, Python `ast`) and are advisory.
3. **You start a session.** One Docker container (`local_lab/runner.py`
   `session_command`) with no network, read-only root, dropped capabilities,
   CPU/memory/pid limits, your workspace folder mounted read-only, running the
   kernel (`local_lab/kernel/kernel.py`) that keeps variables between cells.
4. **You run the graph.** `graph.plan` orders the cells, `graph.preflight` lists
   inputs nobody produces, you approve, `local_lab/graph_run.py` executes them one
   at a time in that kernel and writes outputs back into the notebook.
5. **You save** to the Mainbooks folder (`local_lab/mainbooks.py`), one approved
   folder, atomic writes.
6. **Models** (`/models`, `local_lab/models.py`): Ollama installed natively, chat
   through `POST /api/models/chat` on loopback. Not connected to graphs yet.

Everything that touches the system is a reviewed step with a visible command, and
local-only use needs no website account. That architecture was not changed today.

## 1. Canvas performance (`998d877`)

**Why first:** you reported lag even with 3 cells, and the canvas is the surface
every later feature lives on (the code map in the roadmap will have hundreds of
nodes). Fixing it later would mean rewriting more.

**What was wrong (measured):** every mouse move while dragging did
`placeNode` (write a card's `style.left/top`) and then `drawEdges`, which called
`box()` for every edge endpoint; `box()` read `offsetWidth/offsetHeight`. A read
right after a write forces the browser to re-layout the whole canvas. Headless
Chromium counted **83 forced layouts per mouse move with 30 cells, 8 with 3**. On
a Mac the layer is CSS-scaled and full of textareas and shadows, so each forced
layout is far more expensive than on the Linux box, which is why 3 cells already
felt bad.

**What changed, all in `local_lab/ui/graph.js` + `graph.css`:**
- `sizes` + a `ResizeObserver`: the browser tells us a card's size when it
  changes; `box()` reads the cache and never forces layout during a drag.
- `drawEdges()` rebuilds the SVG only when edges are added or removed;
  `updateEdgesFor(ids)` re-routes just the paths touching moved or resized cards;
  `restyleEdges()` changes classes (fired/selected) without rebuilding.
- `scheduleFrame()`: mouse moves, pan, wheel-zoom and the link preview are
  applied once per `requestAnimationFrame`, so 120 Hz input never does more work
  than the screen can show.
- `select()` repaints two cards instead of all; `applyRunSnapshot()` repaints
  only cards whose run entry changed; run polling adapts 250 ms → 1.5 s.
- `.world { will-change: transform }` so pan/zoom scales a cached raster.

**Numbers (headless Chromium, tested):** JS per drag move 2.0 ms → 0.01 ms at 30
cells; forced layouts 83 → 0; select 5.5 ms → 0.6 ms; keystroke 2.6 ms → 0.35 ms.
The Mac feel is yours to judge (unverified here).

**Two bugs found by the new tests, both older than today:** (a) the dashed link
preview was never hidden after a drop, because the `hidden` attribute does nothing
on SVG elements; (b) the preview ended exactly under the pointer and could steal
the drop target. Both fixed.

**Tests:** `tests/test_canvas_ui.py` (drag, typing, selection, link drag,
pan/zoom in a real browser) and `tests/perf/bench_canvas.py` (the numbers; results
in `tests/perf/results/`). Both skip automatically where Playwright is absent.

## 2. Cell library (`5d2f19a`)

**Why:** your item 2, and it is the building-block mechanism for everything in the
roadmap: automations, per-device graphs and the generic-repo configuration all
need cells that live in one place and can be reused from many Mainbooks.

**What it does:** a global folder of reusable cells, one JSON file per cell, usable
from any Mainbook. Inserting a cell does not copy-and-forget: the Mainbook keeps a
link to the library version, so later the Lab can say *up to date*, *the library
has a newer version → Update*, or *edited here → Push new version*. You fix a cell
in one place and every Mainbook that uses it can pull the fix.

**How, file by file:**
- `local_lab/library.py`: folder approval (`<parent of Mainbooks>/Library`, same
  rules as Mainbooks), `validate_record`, `save` (new name → v1, existing name +
  overwrite → stored version + 1), `listing(query)` search, `insert` (optionally
  chained after a node like the + button), `pull`, `link_state`, `seed`.
- `local_lab/server.py`: `GET /api/library?q=`, `GET /api/library/<name>`,
  `POST /api/library/folder | seed | save | insert | pull`; every graph view now
  carries `library: {node_id: {name, version, latest, state}}`.
- `local_lab/ui/graph.html|css|js`: LIBRARY section in the inspector (search,
  Insert, drag a row onto the canvas), LIBRARY LINK row on the selected cell,
  three approval dialogs.
- `examples/library/*.cell.json`: your ML flow, load data → extract features →
  split → train classifier → evaluate → report, standard library only (a
  pure-Python logistic regression on a synthetic dataset) so it runs in the
  container as it is. Data edges between the six are derived from the code.

**Tests:** `tests/test_library.py` (13, incl. the full HTTP flow) and a browser
test that approves the folder, adds starters, searches, inserts, edits, pushes v2,
detects a v1 copy as behind, pulls, and drags a cell onto the canvas — against the
real in-process service with the real owner-key sign-in. The starter flow runs end
to end in plain Python (tested); inside the Docker session on your Mac it is
unverified.

## 3. Environment per Mainbook (`e383b70`, `557247e`)

**Why:** your item 3. The base image has only the standard library; real work
needs packages, and later (roadmap A3) other languages need other runtimes. The
mechanism had to keep the "no network in the session" rule intact.

**What it does:** a Mainbook writes the packages it needs into its own metadata
(exact pins, `numpy==2.3.3`). The Lab turns the list into a two-line Dockerfile
and an image tag that is a hash of the list, so the same list always means the
same image and two Mainbooks with the same list share one. You review the
Dockerfile and the exact `docker build` command, approve once, the build runs in
the background with its log in the panel. Sessions then use that image with every
limit unchanged. If the image is not built, Start session says so plainly.

**Network honesty:** the build is the only step that uses the network, through
Docker's build network for pip; nothing from the Mac is sent (Dockerfile over
stdin, no context folder). The session keeps `--network=none`.

**How, file by file:** `local_lab/environment.py` (parse, tag, Dockerfile,
command, `Build` background job with bounded log and 15-minute timeout,
`image_ready` via `docker image inspect`, never pulls), `graph.py` (validates the
declaration), `runner.py` (image from settings), `server.py` (`GET
/api/environment`, `POST /api/environment/build {confirm, image}`, the session
gate, `/api/state` reports it), `graph.html|css|js` (ENVIRONMENT panel and dialog).

**Tests:** `tests/test_environment.py` (12, with a fake `docker build`) and a
browser test of the panel. A real build with real packages on a Mac is unverified.

**Known limits, written in `docs/LOCAL_LAB_SETUP.md`:** no apt lines (packages
needing system libraries fail with the pip error in the log); old
`mainaiger-lab-env:*` images accumulate until removed by hand.
